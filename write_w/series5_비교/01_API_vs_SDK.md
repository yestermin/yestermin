# API vs SDK — "API 붙였어요"라고 말했는데 사실은 SDK를 깔았을 때

*시리즈: 그래서 뭐가 다른데 | 1/10*

---

개발자 옆자리에서 이 두 단어를 하루에 열 번쯤 듣는다. 그런데 "API 좀 붙여주세요"라고 말한 사람에게 "그거 SDK 쓰시면 돼요"라는 답이 돌아오면 대화가 묘하게 멈춘다. 둘 다 "남이 만든 기능을 가져다 쓰는 것"이라 대충 같은 말처럼 들리기 때문이다. 같은 말이 아니다. **하나는 약속이고, 하나는 도구 상자다.**

## 1라운드 — 한 줄로 못 박기

**API(Application Programming Interface)**: 프로그램끼리 주고받는 **규칙과 창구 그 자체**. "이 주소로 이런 형식을 보내면 이런 형식으로 답해준다"는 계약서다.

**SDK(Software Development Kit)**: 그 API를 특정 언어·환경에서 편하게 쓰라고 누군가 미리 포장해둔 **개발 키트**. 라이브러리, 예제 코드, 문서, 디버깅 도구 등이 한 묶음으로 들어있다.

식당으로 비유하면 API는 **메뉴판과 주문 창구**다. 뭘 시킬 수 있고 어떻게 말해야 하는지 정해져 있다. SDK는 그 식당이 "집에서도 해 드세요"라며 내놓은 **밀키트**다. 재료, 양념, 조리 설명서가 다 들어있지만, 결국 그 안에서 하는 일은 같은 메뉴를 만드는 것이다.

## 2라운드 — 결정적 차이

| | API | SDK |
|---|---|---|
| 정체 | 인터페이스(규격·약속) | 그 규격을 쓰기 위한 도구 묶음 |
| 형태 | 문서 + 엔드포인트 / 함수 시그니처 | 설치하는 패키지·파일 세트 |
| 언어 의존성 | 웹 API는 대체로 언어 무관 | 언어·플랫폼별로 따로 제공 (파이썬용, iOS용 등) |
| 없으면 | 아예 연동이 불가능 | 불편할 뿐, 직접 호출로 대체 가능 |
| 포함 관계 | SDK 안에 API 호출 코드가 들어있다 | SDK는 API를 감싼다 |

핵심은 마지막 줄이다. **SDK는 대개 API를 포함하지만, API는 SDK를 포함하지 않는다.** 그래서 "SDK 없이 API만 쓴다"는 성립하지만 "API 없이 SDK만 쓴다"는 보통 성립하지 않는다.

또 하나. API는 웹(HTTP) 위에서만 사는 개념이 아니다. 운영체제 API, 라이브러리의 함수 API처럼 네트워크와 무관한 API도 많다. "API = 서버에 요청 보내는 것"이라는 인식은 웹 API가 워낙 흔해서 생긴 착시다.

## 3라운드 — 왜 헷갈리게 됐나

범인은 **회사들의 마케팅 문구**다. 대부분의 서비스가 "우리 API를 쓰세요"라고 홍보하면서 정작 첫 화면에서 내미는 건 `pip install ○○`, `npm install ○○` 같은 SDK 설치 명령어다. 개발자 입장에서 실제로 만지는 건 SDK인데 부르는 이름은 API이니, 두 단어가 한 덩어리로 붙어버린다.

경계가 진짜 흐릿한 경우도 있다. 어떤 회사의 "SDK"는 얇은 함수 몇 개가 전부라 사실상 래퍼 라이브러리에 가깝고, 어떤 "API 클라이언트"는 인증·재시도·캐시까지 다 처리해서 SDK라 불러도 될 만큼 두툼하다. 이 구간에서는 이름이 기능을 정확히 반영하지 못한다. **이름보다 "안에 뭐가 들었나"를 보는 게 맞다.**

## 그래서 언제 뭘

- **SDK가 제공되고, 그 언어를 쓰고 있다면 → SDK.** 인증 토큰 갱신, 재시도, 에러 타입 같은 귀찮은 걸 대신 해준다. 굳이 직접 짜서 버그를 새로 만들 이유가 없다.
- **지원 SDK가 없는 언어·환경이거나, 의존성을 최소로 유지해야 한다면 → API 직접 호출.** HTTP 요청 하나 보내는 게 전부인 경우도 많다.
- **동작이 이상해서 원인을 파야 할 때 → API 문서로 내려가라.** SDK는 편의를 위해 뭔가를 숨기고 있고, 문제는 대개 그 숨겨진 곳에서 난다.

정리하면 이렇다. **API는 "무엇을 할 수 있는가"를 정의하고, SDK는 "그걸 얼마나 편하게 할 것인가"를 정한다.** 기획서에 쓸 때는 "○○ 연동"이라고 쓰는 게 가장 사고가 안 난다.
